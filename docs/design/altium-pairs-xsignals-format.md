# How Altium stores differential pairs and xSignals in a PcbDoc

Altium Designer 26.12.2 wrote the board this note describes on 20 November 2026. The file is the synthetic fixture [PairsXSignals.PcbDoc](../../tests/fixtures/altium/pairs-xsignals/PairsXSignals.PcbDoc), built by [MakePairsFixture.pas](../../tests/altium-wine/MakePairsFixture.pas). Every claim below comes from that file, from Designer reading it back through its own PCB API, or from the scripting names in the installed `ScriptingSystem.dll` and `AdvPcb.rcs`. The layout of `PinPairsSection` and the record format of other Designer versions remain unconfirmed. [Fixture README](../../tests/fixtures/altium/pairs-xsignals/README.md)

## Summary

| Data | Stream | Record | Key fields |
| --- | --- | --- | --- |
| Net class | `Classes6/Data` | text | `KIND=0`, `NAME`, `SUPERCLASS`, `M0..Mn` = net names |
| Differential pair class | `Classes6/Data` | text | `KIND=6`, `M0..Mn` = pair **names** |
| Differential pair | `DifferentialPairs6/Data` | text | `NAME`, `POSITIVENETNAME`, `NEGATIVENETNAME`, `GATHERCONTROL`, `UNIQUEID`, `LAYER=TOP` |
| xSignal class | `SignalClasses/Data` (not `Classes6`) | text | `KIND=10`, `M0..Mn` = xSignal names |
| xSignal | `Board6/Data`, first record | indexed keys | `PINPAIRCOUNT`, `PINPAIRNAMEi`, `PINPAIRPINSi`, `PINPAIRPINUNIQUEIDSi`, `PINPAIRGUIDi`, `PINPAIRCOLORi`, `PINPAIROVERRIDECOLORFORDRAWi` |
| Rules scoped to these | `Rules6/Data` | u16 + text | `SCOPE1EXPRESSION=InDifferentialPairClass('…')`, `InxSignalClass('…')` |

`PinPairsSection/Data` exists but is **empty** (its header count is 0) even though the board has four xSignals. In this version the xSignals are only in `Board6`.

## Record framing

`Classes6`, `SignalClasses`, `DifferentialPairs6`, `Nets6` and `Board6` use the usual Altium text-record framing. Each record is a u32 little-endian byte length followed by `|KEY=VALUE|…` text and a terminating NUL. Each `<Name>/Header` stream holds a u32 record count: Classes6 17, SignalClasses 3, DifferentialPairs6 2 and PinPairsSection 0. `Rules6` records start with an additional u16 before the u32 length. The u16 differs by rule kind: Clearance 0, Width 2, MatchedLengths 4 and DiffPairsRouting 51.

## Classes

`Classes6` and `SignalClasses` share the same keys: `SELECTION`, `LAYER=MULTILAYER`, `LOCKED`, `POLYGONOUTLINE`, `USERROUTED`, `KEEPOUT`, `UNIONINDEX`, `NAME`, `KIND`, `SUPERCLASS`, `M0`…`Mn`, `SELECTED`, `SCHAUTOGENERATEDCLUSTER` and `UNIQUEID`. Auto-generated component classes add `AUTOGENERATEDCLASS=TRUE` and `AUTOGENERATEDCLASSKIND`.

| KIND | Members | Stream | Built-in superclass written here |
| --- | --- | --- | --- |
| 0 | nets | Classes6 | All Nets |
| 1 | components (designators) | Classes6 | All Components, plus auto Top/Bottom/Inside/Outside Board Components |
| 2 | from-tos | Classes6 | All From-Tos |
| 3 | pads | Classes6 | All Pads |
| 4 | layers | Classes6 | Component / Signal / Electrical / All Layers |
| 6 | differential pairs (by pair `NAME`) | Classes6 | All Differential Pairs |
| 7 | polygons | Classes6 | All Polygons |
| 10 | xSignals (by xSignal name) | **SignalClasses** | All xSignals |

The script API also lists in-memory classes "All Nets" with kind 11 and "All xNets" with kind 12. They are not saved. Superclasses (`SUPERCLASS=TRUE`) carry no `M` keys, so importers should skip them or expand them themselves. The scripting enum names the kinds `eClassMemberKind_Net`, `_Component`, `_FromTo`, `_Pad`, `_Layer`, `_DifferentialPair`, `_Polygon`, `_Signal` (xSignal) and `_xNet`.

## Differential pairs

```text
|SELECTION=FALSE|LAYER=TOP|LOCKED=FALSE|POLYGONOUTLINE=FALSE|USERROUTED=TRUE|KEEPOUT=FALSE|UNIONINDEX=0
|POSITIVENETNAME=PCIE_TX_P|NEGATIVENETNAME=PCIE_TX_N|NAME=PCIE_TX|GATHERCONTROL=FALSE|UNIQUEID=…
```

Pairs refer to nets by name. `Nets6` records carry no pair field, so the pairing exists only here. Pair names need not follow the `_P`/`_N` suffix convention: the USB pair uses `USB_DP`/`USB_DM`. A pair class lists pair names, not net names.

## xSignals

Designer's scripting API calls an xSignal a *pin pair*: `IPCB_PinPair`, `Board.PinPairsManager`, and the `PCB:ManagePinPairs` command behind the xSignals menu and wizard. They are saved as indexed keys in the first `Board6` record. Here `i` runs from 0 to `PINPAIRCOUNT-1`:

```text
PINPAIRCOUNT=4
PINPAIRNAME0=PCIE_TX_P_XS
PINPAIRCOLOR0=7709086
PINPAIROVERRIDECOLORFORDRAW0=FALSE
PINPAIRPINS0=U1-3,C1-1,C1-2,J1-3
PINPAIRPINUNIQUEIDS0=PHWGSKKT,KTPEBONA,CEXTXDLH,OSCNRRQO
PINPAIRGUID0={505FF14D-1DF0-4BFE-924F-31F3894569A9}
PINPAIRNAME2=USB_DP_XS
PINPAIRPINS2=U1-1,J1-1
PINPAIRPINUNIQUEIDS2=WPRYYLAI,HBJDAPLG
```

- `PINPAIRPINS` is an ordered path of `Designator-PadName` entries. The first entry is the start pad and the last is the end pad. The script supplied only the two endpoints (U1-3 and J1-3). Designer added both pads of the series capacitor C1 itself, so an xSignal through an AC-coupling cap crosses two nets: PCIE_TX_P and PCIE_TX_C_P.
- `PINPAIRPINUNIQUEIDS` holds the matching pad `UNIQUEID`s. They resolve through `UniqueIDPrimitiveInformation/Data` (`PRIMITIVEINDEX=n|PRIMITIVEOBJECTID=Pad|UNIQUEID=…`), where `PRIMITIVEINDEX` is the pad's position in `Pads6`. Designer can rebuild the path from the designators or from the unique IDs.
- An xSignal's class membership is stored only in `SignalClasses`, by name.

## Rules that reference them

Rules store the scope as a query string: `SCOPE1EXPRESSION=InDifferentialPairClass('HS_PAIRS')` and `SCOPE1EXPRESSION=InxSignalClass('PCIE_TX_XSIGNALS')`, each with `SCOPE2EXPRESSION=All`. The MatchedLengths rule also stores `TOLERANCE=10mil`, `CHECKNETSINDIFFPAIR=FALSE`, `CHECKDIFFPAIRVSDIFFPAIR=TRUE`, `CHECKXSIGNALS=TRUE` and `CHECKOTHERS=TRUE`. DiffPairsRouting stores `MAXLIMIT`, `MINLIMIT`, `MOSTFREQGAP`, `MAXUNCOUPLEDLENGTH` and per-layer `<LAYER>_MINWIDTH`/`_MAXWIDTH`/`_PREFWIDTH` for `TOPLAYER`, `MIDLAYER1`…`MIDLAYER30` and `BOTTOMLAYER`.

## Other observations

- **ASCII PcbDoc is lossy.** Saving as `PCB ASCII File` writes the legacy `VERSION=5.01` text format. It keeps `RECORD=DifferentialPair` and net classes, but it drops pair classes, xSignal classes and xSignals. It rewrites query scopes as `Board` and keeps the original expression only in `COMMENT=Protel DXP Scope 1 Expression Was: …`. Use binary files as the import reference.
- Once online DRC has run, saving also writes violation streams such as `TDiffPairsViolation/Data` (`RULEINDEX`, `PRIM1ID=DifferentialPair`, `DESCRIPTION=[Uncoupled Length = …]`), `TMinWidthStubTrackViolation` and `TSilkToSilkClearanceViolation`. After Designer has loaded a TrueType font in the session, a save can embed it in `EmbeddedFonts6` (Arial, about 0.4 MB) even when every text uses a stroke font. These streams belong to the session, not to the design.
- In the script API, `IPCB_PinPairsManager` provides `CreateFromPins(IInterfaceList)`, `CreateFromPinsDescriptors`, `CreateFromPinsUniqueIDs`, `AssignPinPairClass(list, className)`, `CreatePinPairsFromComponent`, `CreatePinPairsFromConnectedNets`, `PinPairsCount`, `PinPairs[i]` and `GetPinPairOf(primitive)`. The wizard is `PCB:ManagePinPairs` with `Action=xSignalsWizard` (or `CreatePinPair`, `CreatePinPairsBetweenComponents`, `CreatePinPairsFromConnectedNets`, `ManagePinPairs`).

## Consequences for Waffle

- The importer can treat the pair and class layouts above as confirmed. Read xSignals from the `Board6` `PINPAIR*` keys and xSignal classes from `SignalClasses`. Keep a fallback for a non-empty `PinPairsSection` until another version shows its layout.
- An exporter can write xSignals as `PINPAIR*` keys in the `Board6` record, using `PINPAIRPINS` endpoints and including series pads. Whether Designer accepts a file without `PINPAIRPINUNIQUEIDS` or `PINPAIRGUID` has not been tested.
