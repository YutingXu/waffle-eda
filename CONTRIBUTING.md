# Contributing to Waffle EDA

Waffle EDA is MIT-licensed (see `LICENSE`). By contributing, you agree that your contribution is released under the same license.

AI-assisted contributions are welcome. Please open an issue before starting a large change so we can agree on the approach together.

## Clean-room interoperability policy
Waffle reads and writes file formats used by other EDA tools, including Altium Designer®. To keep that work lawful and to respect other vendors' terms:

1. **Never decompile, disassemble or reverse-engineer another vendor's software.** Altium's EULA (§3.3) forbids its licensees from doing this to Altium's software and documentation. Don't contribute anything derived from that, and don't contribute information obtained under a non-disclosure agreement or Altium's confidentiality terms.
2. **Implement formats only from permitted sources:**
   - design files you created or have the right to use;
   - publicly available specifications (for example, Gerber X2 from Ucamco, Excellon, IPC standards you are licensed to read);
   - independently written, compatibly licensed open-source readers. Say which in the pull request, and don't copy code with an incompatible license.
3. **Don't copy vendor documentation text, screenshots, icons, logos, fonts or component libraries into the repository.** Link to the vendor's documentation instead.
4. **Use other companies' marks only descriptively and accurately.** Examples: "imports Altium Designer .PcbDoc files", "Altium-style key sequences". Never use them in Waffle's name, logo, package names or anything that implies endorsement. Mark the first prominent use in user-facing documentation with ® or ™.
5. **Test fixtures:** don't commit third-party design files unless their license allows redistribution. Name the source and license in the test file. Prefer synthetic fixtures generated by tests.
6. **When adding a third-party library, font, glyph set or data table:** update `THIRD_PARTY_NOTICES.md` and ship its license text beside it.

## Development
- Run `python3 scripts/prepare-assets.py` before opening `app/index.html` or running an individual suite in a new checkout. The package and main test runners prepare assets automatically.
- Work on the readable JavaScript in `app/` and the built-ins in `extensions/`. Rerun preparation after changing a worker input, locale or extension. `python3 scripts/prepare-assets.py --check` verifies the local outputs without writing any files.
- Run `node tests/run.cjs` (Node 18+) for the regression suite.
- Discuss proposed features and priorities in the [issue tracker](../../issues).

### Changes that react to an edit

Use the undo history's change record to identify affected documents, objects and dependencies. Paint their old and new bounds in the first frame. Share that record with connectivity, connection lines, live copper previews and nearby rule checks. Spread follow-up work over bounded slices and leave lower-priority work until idle. A superseding edit cancels stale work and preserves damage accrued since each consumer last published.

Use full recalculation when the relevant change is genuinely unknown, such as a project replacement or a gap in retained history. Test every incremental path against its full equivalent, including undo and redo. Start optional preparation only on a specific user signal, withdraw it when the signal disappears, and disable it in Efficiency mode.
